# План MVP flakCRM

- **Статус:** исторический план CRM-домена; сетевой режим — ADR 0003 и `network.md`
- **Текущий milestone:** M0 — каркас и данные
- **Дата:** 2026-11-10
- **Документы:** `docs/adr/0001-stack.md`, `docs/adr/0002-single-user-local-mode.md`, `docs/adr/0003-multi-tenant-network.md`, `docs/architecture/network.md`, `docs/architecture/domain.md`, `docs/architecture/api.md`

## 1. Цель и границы

Один пользователь, продающий IT-услуги, ведёт локальную CRM на своей машине: хранит компании, контакты, лиды и сделки, двигает сделки по воронке, фиксирует активности и задачи, видит состояние пайплайна и выгружает данные в CSV. Авторизации нет; данные — в SQLite. Подробнее — ADR 0002.

**Входит в MVP:** дашборд, компании, контакты, лиды и конвертация, сделки, воронка/канбан/таблица, активности, задачи, timeline на карточках, глобальный поиск, CSV-экспорт, мягкое удаление, аудит, история стадий, оптимистическая блокировка сделки, деньги в минорных единицах, UTC, IT-атрибуты (отрасль/стек/размер, тип услуги, источник).

**Явно не входит:** аутентификация, роли, несколько пользователей/workspace, несколько воронок и редактирование стадий, импорт, вложения, сохранённые представления, уведомления, интеграции, вебхуки, телефония, email/calendar sync, биллинг, мобильные приложения, AI, фоновые очереди, BI-слой, корзина/восстановление, настройки workspace через UI.

**Отличие от `AGENTS.md`:** пользователь сузил MVP до одного пользователя без авторизации и без импорта/уведомлений/сохранённых представлений. Это зафиксировано ADR 0002 и разделом 9. Остальные инварианты `AGENTS.md` действуют в адаптированном виде: workspace берётся из контекста сервера, деньги/UTC/аудит/версия/дедупликация/валидация сохраняются.

## 2. Акторы и основной сценарий

| Актор | Возможности |
| --- | --- |
| Локальный пользователь (`owner`) | все операции MVP в workspace `1` |
| Vite dev server | proxy `/api` на Express |
| Express production | API + статика SPA |

**Основной сценарий приёмки:**

1. Пользователь открывает дашборд, видит пустые состояния и кнопки создания.
2. Создаёт компанию с URL сайта; домен нормализуется, повтор блокируется.
3. Создаёт контакт и привязывает к компании; дубль email предупреждается.
4. Создаёт лид из LinkedIn, конвертирует в компанию/контакт/сделку; повторная конвертация не создаёт дублей.
5. На канбане двигает сделку по стадиям; в другом окне со старой версией получает конфликт, а не перезапись.
6. Закрывает сделку как won; дашборд и таблица отражают результат.
7. Добавляет звонок, встречу и задачу; они видны в timeline и на дашборде.
8. Находит запись глобальным поиском и выгружает сделки в CSV.
9. Удаляет контакт; он исчезает из списков и поиска, аудит сохраняет факт удаления.

### UI-маршруты и состояния

| Маршрут | Экран | Ключевое поведение |
| --- | --- | --- |
| `/` | Dashboard | период, валюта, стадии, won/lost, задачи, последние активности |
| `/companies`, `/companies/new`, `/companies/:id`, `/companies/:id/edit` | Компании | список с фильтрами в URL, деталь с контактами/сделками, форма |
| `/contacts`, `/contacts/new`, `/contacts/:id`, `/contacts/:id/edit` | Контакты | список, деталь с компанией и сделками, форма |
| `/leads`, `/leads/new`, `/leads/:id`, `/leads/:id/edit` | Лиды | список, деталь с CTA «Конвертировать», форма |
| `/deals?view=board\|table`, `/deals/new`, `/deals/:id`, `/deals/:id/edit` | Сделки | канбан по умолчанию, таблица, карточка с вкладками «Обзор/Активности/Задачи/История» |
| `/tasks` | Задачи | все задачи, фильтры «открытые/просроченные/выполненные» |
| `*` | 404 | ссылка на дашборд |

- Глобальный поиск — оверлей по `Cmd/Ctrl+K`, без отдельного маршрута; результаты стрелками и Enter.
- Фильтры, сортировка и страница списка хранятся в query string; возврат назад сохраняет состояние.
- Состояния: скелетон загрузки, пустое состояние с CTA, ошибка с повтором, 404 для отсутствующей записи; формы показывают серверные ошибки у полей и общий конфликт.
- Канбан: drag-and-drop и клавиатурное «Переместить на стадию»; при `409 VERSION_CONFLICT` — сообщение, refetch, без оптимистичной потери.
- Доступность: семантические таблицы, подписи полей, focus trap и Esc в диалогах, `aria-live` для тостов, контраст AA, управление с клавиатуры, адаптивность от 320 px.
- Локализация: все строки в `src/i18n/ru.ts`; даты/деньги форматируются централизованно в таймзоне текущего пользователя.

## 4. Критерии приёмки по срезам

### M0

- `npm ci` (или `npm install`) → `npm run db:migrate` на пустом `DATABASE_PATH` → `npm run dev`; БД создана, повторный запуск не дублирует seed.
- `GET /api/health` → `200 {status:"ok",db:"ok"}`; `GET /api/v1/meta` → workspace `1`, user `1`, pipeline с 5 стадиями, список валют и enum.
- Неизвестный `/api/v1/nope` → JSON `404 NOT_FOUND`; неизвестное поле в POST → `400 VALIDATION_ERROR`; `workspaceId` в теле → `400`.
- `npm test`, `npm run typecheck`, `npm run lint`, `npm run build` проходят; `npm start` раздаёт собранный SPA и API с одного порта.
- SPA: layout, навигация, 404, провайдеры Query, API-клиент, глобальный error boundary; на 320 px нет горизонтального переполнения корпуса.

### M1

- Нормализация: `https://www.Example.com/about` → `example.com`; схема, путь и порт отбрасываются; IDN → punycode.
- Создание второй активной компании с тем же доменом → `409 DUPLICATE_COMPANY`; после мягкого удаления первой — разрешено.
- Контакт без `allowDuplicate` с существующим email → `409 DUPLICATE_CONTACT`; с флагом — создаётся; оба видны в списке.
- Обновление компании/контакта пишет `AuditEvent` только по отслеживаемым полям; заметки в аудит не попадают.
- Списки: пагинация, `total`, сортировка, фильтры, поиск по кириллице в upper/lower case; pageSize > 100 → 400.
- UI: загрузка/пусто/ошибка, форма с серверными ошибками, inline-предупреждение дубля, подтверждение удаления, клавиатурная навигация.

### M2

- Первая конвертация: `200`, `alreadyConverted:false`, `created.deal:true`; компания по домену email переиспользуется, контакт по email — тоже.
- Повтор с пустым телом: `200`, те же ID, все `created:false`, в БД нет новых строк.
- Невалидная стадия/валюта/компания: `4xx`, ни одной частичной записи (проверка счётчиков до/после).
- PATCH конвертированного лида с `companyName` → `422 LEAD_CONVERTED`; только `notes` — `200`.
- UI: диалог с предзаполнением, выбор существующей компании или создание, успех ведёт на сделку, повторный заход показывает ссылки на созданные записи.

### M3

- Создание сделки: `version=1`, стартовая запись истории `fromStage=null`, аудит create.
- Смена стадии: история + аудит + `version+1`; та же стадия — без записи; stale версия — `409`, сделка и история не изменились.
- `lost` без причины → `422`; с причиной → `closedAt` заполнен; `open` очищает; won очищает причину.
- Смена стадии закрытой сделки → `422 DEAL_CLOSED`.
- Удаление компании с открытой сделкой → `409 COMPANY_HAS_OPEN_DEALS`; после won/lost/удаления сделки — `204`.
- Board: пустые стадии присутствуют, `dealCount/amountMinor` не зависят от `limitPerStage`, `truncated` корректен, только open и выбранная валюта.
- UI: канбан drag-and-drop и альтернативное клавиатурное перемещение; конфликт версии — сообщение и refetch без потери данных; таблица и фильтры в URL.

### M4

- Активность с несуществующей/удалённой целью → `422 INVALID_REFERENCE`; привязка после создания не меняется.
- Удаление сделки каскадно скрывает её активности и задачи; в аудите родителя есть `cascaded`-счётчики.
- Задача `done` выставляет `completedAt`, `open` очищает; `isOverdue` считается по таймзоне workspace.
- Дашборд: won/lost только в периоде по `closedAt`; pipeline — снимок; суммы только выбранной валюты; winRate `null` без закрытых; границы месяца в `Europe/Moscow` не съезжают на UTC.
- UI: timeline сделки (активности + история стадий + аудит без `stage_change`) отсортирован по времени; задачи и активности доступны с карточек компании/контакта/лида/сделки.

### M5

- Поиск: минимум 2 символа, группы с `total` и урезанными `items`, кириллица без учёта регистра, удалённые не находятся.
- CSV: BOM, CRLF, корректные кавычки для `,`, `"`, перевода строки; значение `=1+1` экранировано апострофом; лимит и заголовок усечения; ошибки — JSON.
- 10 000 компаний / 5 000 сделок: p95 списка < 150 мс, dashboard < 300 мс, board < 250 мс на локальной машине (замер QA).
- QA-матрица: негативные сценарии, права/изоляция (fixed workspace), регрессии, a11y (фокус, Esc, aria-live, контраст), 320/768/1280, production build.

## 7. Риски и допущения

| Риск | Влияние | Митигация |
| --- | --- | --- |
| API `node:sqlite` в Node 26 отличается от ожидаемого | блокирует старт | адаптер в `server/db/open.ts`; M0 фиксирует точный API на целевой версии; без ORM |
| SQLite single-writer / долгий экспорт | таймауты записи | WAL, busy_timeout, короткие транзакции, лимит экспорта 100k |
| Однопользовательский режим без auth | данные доступны любому с доступом к машине | bind 127.0.0.1, запрет LAN, ADR 0002; auth — отдельный ADR |
| Канбан с большим числом сделок | тяжёлый рендер | board-агрегаты, `limitPerStage`, `truncated`, клиентская виртуализация только при доказанной необходимости |
| Смешение валют в суммах | неверные отчёты | суммы только в одной валюте, фильтр и `availableCurrencies`; валюты с экспонентой 2 |
| Кириллица в `LIKE/lower` SQLite | поиск не находит | колонки `*_norm`, нормализация в JS, тесты на регистр |
| Мягкое удаление оставляет ссылки | «висячие» связи | явные правила §7 domain.md, резолв в `null`, блокировка удаления компании с open-сделками |
| CSV-инъекции | риск при открытии в Excel | префикс `'` для опасных первых символов, тест |
| Границы периода/таймзоны | неверный won/lost | единая функция границ в workspace tz, тест на переход месяца |
| Express 5 SPA-fallback и `/api` | 404/HTML вместо JSON | fallback только GET вне `/api`, отдельный JSON-404, тест |
| Расхождение контракта и реализации | дефекты интеграции | Zod/DTO в `shared/`, QA по api.md, запрет молчаливых изменений |
| Расползание объёма (импорт, интеграции) | срыв MVP | явные границы §1, новые срезы только через план/ADR |
| Пустая БД и seed стадий | пользователь не может настроить воронку | принято для MVP; настройка стадий — следующий срез |

**Допущения:**

- Интерфейс и сообщения — на русском; строки централизованы в `src/i18n/ru.ts`. Названия стадий — данные seed на русском.
- Базовая валюта — `USD` по умолчанию, таймзона — `UTC`; меняются env при первом запуске. Пользователь может указать свои значения до создания БД.
- Одна воронка, пять фиксированных стадий; won/lost — статусы, не стадии.
- Импорт, уведомления, сохранённые представления, вложения, интеграции — вне MVP; CSV только экспорт.
- Расчётный объём — §11 domain.md; при превышении на порядок требуется отдельное решение (FTS5/PostgreSQL) и ADR.
- Резервное копирование — ручное копирование файла БД (с остановкой или `VACUUM INTO`); автоматического бэкапа в MVP нет.

## 8. Порядок приёмки

1. Владелец зоны объявляет срез готовым и прикладывает команды/результаты.
2. QA проходит матрицу своего этапа и фиксирует severity.
3. Блокеры возвращаются backend/frontend; после исправления — повторный прогон.
4. `crm-lead` лично запускает проверки §6, читает diff и проходит сценарий §2.
5. Обновляются `plan.md` (текущий milestone), при необходимости ADR и `api.md`/`domain.md`.
6. Только после этого начинается следующий этап.

## 9. Границы изменений `AGENTS.md`

- Стек из `AGENTS.md` («не зафиксирован») заменён ADR 0001; `crm-lead` должен обновить раздел стека.
- Роли и авторизация отложены ADR 0002; матрица прав MVP — один `owner`.
- `SavedView`, `Notification`, `Attachment`, импорт, `IntegrationConnection`, `ExternalRef` не реализуются в MVP. Это осознанное сужение пользователем, а не забытые пункты.
- Инварианты `AGENTS.md` 1 (workspace), 3–14 действуют; 2 (роли) и часть 14 (импорт) заменены/отложены ADR 0002 и границами MVP.
- `crm-integrator` в MVP не задействован: CSV-экспорт реализует backend. Импорт и внешние адаптеры — следующий срез с участием интегратора.
