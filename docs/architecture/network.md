# Архитектура сети бизнесов

Документ описывает текущую мультитенантную сборку. Историческое описание
однопользовательской CRM — в `plan.md`, `domain.md` и ADR 0001–0002.

## 1. Компоненты

```
Браузер владельца ──┐
                    ├── Express (один процесс)
Браузер гостя ──────┘     ├── /api/auth      реестр, вход, сессии
                          ├── /api/network   конструктор, заявки (нужна сессия)
                          ├── /api/v1        CRM бизнеса (нужна сессия)
                          ├── /api/public    опубликованные сайты и заявки
                          └── /, /s/:slug    SPA из dist/
                                      │
                     ┌────────────────┴────────────────┐
                     │                                 │
              registry.db                       tenants/*.db
       аккаунты, бизнесы, членство,          CRM, каталог, заявки
                сессии                       одного бизнеса
```

- **Реестр** (`REGISTRY_PATH`) — общий для всех бизнесов.
- **База бизнеса** (`tenant.db_path`) — отдельный SQLite-файл. Внутри неё
  `workspace.id = 1`, `app_user.id = 1`; это локальная идентичность бизнеса,
  а не глобальный пользователь сети.
- **`AsyncLocalStorage`** хранит базу активного запроса. Роутеры `/api/v1`
  получают прокси `Db`, поэтому доменные сервисы не знают о мультитенантности.

## 2. Модель реестра

`PRAGMA user_version = 1`.

| Таблица | Назначение |
| --- | --- |
| `tenant` | `id`, уникальный `slug`, название, вертикаль, путь к БД |
| `account` | email (уникальный), имя, `password_hash` (`scrypt`) |
| `membership` | связь аккаунта и бизнеса; пока только роль `owner` |
| `session` | SHA-256 токена, аккаунт, активный бизнес, срок жизни |

Пароль и токен в открытом виде не хранятся. Cookie opaque; по реестру нельзя
восстановить токен.

### Провижининг

`provisionTenant()`:

1. генерирует уникальный slug;
2. создаёт запись `tenant` с новым путём `tenant-<random>.db`;
3. открывает БД, применяет миграции, создаёт `site_config` и локальную
   идентичность;
4. добавляет членство владельца.

Если шаг 3–4 падает, запись реестра удаляется. Файл БД может остаться
осиротевшим — это осознанный выбор в пользу сохранности данных.

## 3. Модель базы бизнеса

`PRAGMA user_version = 2`.

### CRM (версия 1)

`workspace`, `app_user`, `membership`, `pipeline`, `stage`, `company`,
`contact`, `lead`, `deal`, `deal_stage_history`, `activity`, `task`,
`audit_event`.

### Сайт (версия 2)

| Таблица | Поля |
| --- | --- |
| `site_config` | одна строка `id = 1`: вертикаль, название, слоган, описание, контакты, часы, цвет, обложка, `is_published` |
| `site_item` | каталог: `kind` (`dish`/`service`/`room`), название, описание, цена в копейках, длительность, вместимость, фото, активность, позиция |
| `site_request` | заявка: код, гость, телефон, email, дата/время, выезд, гости, позиция каталога, комментарий, `lead_id` |

Ограничения:

- цена хранится в минорных единицах и не может быть отрицательной;
- `site_request.lead_id` обязателен и ссылается на лид той же базы;
- код заявки уникален в базе бизнеса;
- при удалении позиции каталога ссылка в заявке становится `NULL`
  (`ON DELETE SET NULL`), сама заявка сохраняется.

## 4. Поток публичной заявки

```
POST /api/public/sites/:slug/requests
  → найти tenant по slug в реестре
  → открыть его БД
  → проверить is_published
  → проверить поля по вертикали
  → BEGIN IMMEDIATE
      создать lead (source='website', serviceType=<vertical>)
      создать site_request(lead_id)
    COMMIT
  → вернуть { code, message }
```

В лид попадают:

- `companyName` — название сайта;
- `contactName` — имя гостя;
- `phone`, `email`;
- `source = website`;
- `serviceType = restaurant | service | tourism`;
- `notes` — дата/время/гости/позиция/комментарий/код заявки.

Статус `site_request` не хранится отдельно: API читает `lead.status`.
Обновление статуса в конструкторе вызывает доменный `updateLead`. Если лид уже
сконвертирован, изменение статуса отклоняется с `LEAD_CONVERTED`.

## 5. Аутентификация и доступ

### Регистрация

`POST /api/auth/register` создаёт аккаунт и первый бизнес одной операцией.
Ответ — публичная сессия без `password_hash` и `db_path`.

### Вход

Email + пароль. Проверка `scrypt` через `timingSafeEqual`. После успеха
создаётся сессия на 7 дней.

Cookie:

```
flakcrm_session=<opaque>;
HttpOnly; SameSite=Lax; Path=/;
Secure (при COOKIE_SECURE=true);
Expires=<через 7 дней>
```

Дополнительно принимается `Authorization: Bearer <token>`.

### Защита входа

- не более 10 неудачных попыток на пару IP + email за 15 минут;
- счётчик в памяти процесса, сбрасывается при рестарте;
- успешный вход очищает счётчик;
- ответ на неверный email и пароль одинаковый.

### Изоляция

1. `requireSession` находит сессию по хэшу токена.
2. Проверяет срок и наличие бизнеса в членстве аккаунта.
3. Открывает базу бизнеса и запускает остальные middleware внутри
   `AsyncLocalStorage`.
4. `/api/network` и `/api/v1` без сессии возвращают `401 UNAUTHORIZED`.
5. Публичный API не принимает cookie-сессию как основание доступа: он работает
   только со slug опубликованного сайта.

## 6. API

Все ответы об ошибках имеют форму:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте заполнение полей.",
    "details": [{ "path": "phone", "message": "..." }],
    "requestId": "..."
  }
}
```

`POST`/`PATCH` требуют `Content-Type: application/json`.

### Служебное

| Метод | Путь | Доступ |
| --- | --- | --- |
| `GET` | `/api/health` | без авторизации |

### Аккаунт и бизнесы

| Метод | Путь | Тело / результат |
| --- | --- | --- |
| `POST` | `/api/auth/register` | `businessName`, `vertical`, `email`, `name`, `password` → `SessionInfo`, 201 |
| `POST` | `/api/auth/login` | `email`, `password` → `SessionInfo` |
| `POST` | `/api/auth/logout` | удаляет сессию, 204 |
| `GET` | `/api/auth/me` | текущий `SessionInfo` |
| `POST` | `/api/auth/switch` | `tenantId` → `SessionInfo` |
| `POST` | `/api/auth/tenants` | `name`, `vertical`, необязательный `slug` → новый бизнес, 201 |

`SessionInfo`:

```json
{
  "account": { "id": 1, "email": "owner@example.ru", "name": "Владелец" },
  "tenant": { "id": 1, "slug": "tihiy-dvorik", "name": "Тихий дворик", "vertical": "restaurant" },
  "tenants": [ ... ]
}
```

Создание бизнеса не переключает активную сессию; клиент явно вызывает
`/api/auth/switch`.

### Конструктор (нужна сессия)

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/network/site` | профиль сайта + каталог |
| `PUT` | `/api/network/site` | профиль; slug проверяется на уникальность |
| `POST` | `/api/network/site/items` | добавить позицию |
| `PATCH` | `/api/network/site/items/:id` | изменить позицию |
| `DELETE` | `/api/network/site/items/:id` | удалить позицию, 204 |
| `POST` | `/api/network/site/publish` | `{ "isPublished": true }` |
| `GET` | `/api/network/requests` | последние 200 заявок |
| `PATCH` | `/api/network/requests/:id` | `{ "status": "contacted" }` |

Статусы заявки: `new`, `contacted`, `qualified`, `disqualified`.

### Публичный сайт

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/public/sites/:slug` | опубликованный сайт + активный каталог |
| `POST` | `/api/public/sites/:slug/requests` | создать заявку |

Тело заявки:

```json
{
  "guestName": "Амина",
  "phone": "+7 928 111-22-33",
  "email": null,
  "requestedDate": "2026-12-01",
  "requestedTime": "19:30",
  "checkOut": null,
  "guests": 4,
  "itemId": null,
  "comment": "Столик у окна"
}
```

Обязательные поля по вертикалям:

- ресторан — `requestedDate`, `requestedTime`, `guests`;
- туризм — `requestedDate`, `guests`; `checkOut` необязателен, но если указан,
  должен быть позже даты заезда;
- сервис — только имя и телефон; дата и позиция необязательны.

### CRM

`/api/v1/*` — существующий CRM API. Полное описание путей и полей —
в `api.md`; теперь каждый запрос требует сессию и выполняется в базе активного
бизнеса.

## 7. Фронтенд

| Путь | Экран |
| --- | --- |
| `/login`, `/register` | вход и создание первого бизнеса |
| `/` | дашборд активного бизнеса |
| `/leads`, `/deals`, `/companies`, `/contacts`, `/tasks`, `/activities` | CRM |
| `/builder` | профиль сайта и каталог |
| `/builder/requests` | заявки, статусы и переход к лиду |
| `/s/:slug` | публичный сайт без авторизации |

`SessionProvider` загружает `/api/auth/me`. При смене бизнеса он обновляет
сессию и сбрасывает данные остальных запросов, чтобы на экране не остались
данные предыдущего бизнеса.

## 8. Ошибки и коды

| Код | HTTP | Когда |
| --- | --- | --- |
| `VALIDATION_ERROR` | 422 | Zod или бизнес-валидация |
| `UNAUTHORIZED` | 401 | нет или истекла сессия |
| `INVALID_CREDENTIALS` | 401 | неверный email/пароль |
| `TOO_MANY_ATTEMPTS` | 429 | превышен лимит входа |
| `EMAIL_TAKEN` | 409 | регистрация существующего email |
| `SLUG_TAKEN` | 409 | занятый адрес сайта |
| `FORBIDDEN` | 403 | нет членства в бизнесе |
| `NO_BUSINESS` | 403 | у аккаунта нет бизнесов |
| `NOT_FOUND` | 404 | сайт, заявка, позиция или маршрут |
| `ITEM_UNAVAILABLE` | 422 | позиция скрыта |
| `LEAD_CONVERTED` | 422 | попытка сменить статус конвертированного лида |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | тело не JSON |
| `METHOD_NOT_ALLOWED` | 405 | неподдерживаемый метод |

## 9. Эксплуатация

### Запуск

```bash
npm ci
npm run build
NODE_ENV=production COOKIE_SECURE=true DATA_DIR=/var/lib/flakcrm npm start
```

`HOST` по умолчанию `127.0.0.1`. Для внешнего доступа поставьте reverse proxy
и задайте `HOST=0.0.0.0`; TLS завершайте на прокси.

### Резервное копирование

Согласованная копия — это **весь** `DATA_DIR`:

- `registry.db` + WAL/SHM;
- `tenants/*.db` + WAL/SHM.

Проще всего остановить процесс и скопировать каталог. Для горячей копии
используйте `sqlite3 <db> ".backup '<copy>'"` для каждого файла, начиная с
реестра.

### Восстановление

1. Остановить сервер.
2. Вернуть `registry.db` и `tenants/` на место.
3. Проверить, что пути в `tenant.db_path` существуют.
4. Запустить сервер и проверить `/api/health`, вход и публичный сайт.

### Диагностика

- `GET /api/health` — статус реестра, число бизнесов, версия, uptime.
- `X-Request-Id` в ответе и в логах ошибок.
- Ошибки 500 логируются с request id и стеком; клиенту стек не отдаётся.

### Ограничения масштабирования

- один процесс на `DATA_DIR`;
- все открытые БД живут в кэше процесса;
- список заявок — последние 200;
- rate limit в памяти;
- нет горизонтального шаринга SQLite по сети.

## 10. Проверки

`server/tests/network.test.ts` поднимает реальный Express на случайном порту с
временным каталогом и проверяет:

- регистрацию и cookie;
- отсутствие утечки `password_hash` и `db_path`;
- запрет доступа без сессии;
- изоляцию компаний между бизнесами;
- публикацию, черновик, публичную заявку и статус лида;
- создание второго бизнеса, переключение и запрет чужого tenant.

Старые тесты CRM (`server/tests/api.test.ts`) работают через `createApp(db)` и
проверяют доменную логику без сети.
