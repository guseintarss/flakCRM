# ADR 0001 — Стек MVP flakCRM

- **Статус:** принят; стек действует, ограничение «публичных страниц нет» заменено ADR 0003
- **Дата:** 2026-11-10
- **Область:** весь проект
- **Связанные документы:** `docs/adr/0002-single-user-local-mode.md`, `docs/adr/0003-multi-tenant-network.md`, `docs/architecture/network.md`, `docs/architecture/plan.md`, `docs/architecture/domain.md`, `docs/architecture/api.md`

> Актуальная архитектура доступа и публичных сайтов — в ADR 0003 и
> `docs/architecture/network.md`. Этот документ фиксирует выбор стека.

## Контекст

flakCRM создаётся с нуля как локальная CRM для одного пользователя, который продаёт IT-услуги. Внешние сервисы, платные аккаунты и облачная инфраструктура не допускаются. Репозиторий пуст: платформенного кода, зависимостей и CI нет.

Требования, влияющие на выбор:

- модульный монолит, одна реляционная БД, без микросервисов, очередей и event sourcing на MVP;
- типобезопасные контракты между сервером и клиентом;
- локальный запуск одной-двумя командами, миграции и тесты «из коробки»;
- зрелая экосистема и низкая цена поддержки одним разработчиком;
- работа на машине пользователя без внешней инфраструктуры;
- интерфейс — SPA с быстрыми списками, канбаном и формами; SEO и SSR не нужны.

Стек зафиксирован пользователем. Альтернативы в разделе ниже объясняют цену решения и границы, в которых его нельзя менять без нового ADR; это не приглашение к пересмотру.

## Решение

| Слой | Решение |
| --- | --- |
| Язык | TypeScript, `strict: true`, ESM |
| Runtime | Node.js 26 |
| HTTP-сервер | Express 5 |
| БД | SQLite, файл `data/flakcrm.db`, доступ через встроенный `node:sqlite` |
| Доступ к данным | Prepared statements и SQL в repository-модулях, без ORM |
| Валидация и контракты | Zod-схемы в `shared/`, TypeScript-типы выводятся из схем |
| Frontend | React 19, Vite, React Router, TanStack Query |
| Стили | собственный CSS: CSS-переменные, модульные файлы по экранам, без Tailwind и UI-китов |
| Тесты сервера | `node:test` + `tsx`, HTTP-тесты через реальный сервер на эфемерном порту, БД `:memory:` |
| Миграции | нумерованные SQL-файлы, forward-only, применяются при старте и командой `npm run db:migrate` |
| Сборка | `tsc` для сервера в `dist/server`, Vite для клиента в `dist/client` |
| Production | Express раздаёт `dist/client`, API — `/api/v1`, SPA-fallback только для GET вне `/api` |
| Dev | Vite на `5173` с proxy `/api` → Express на `127.0.0.1:3000` |
| Логирование | структурированный stdout: request id, метод, путь, статус, длительность; без тел и PII |

### Структура репозитория

```text
/
├─ server/                 # модульный монолит
│  ├─ index.ts             # bootstrap, static, SPA fallback
│  ├─ app.ts               # сборка Express-приложения без listen
│  ├─ config.ts            # env + значения по умолчанию
│  ├─ db/
│  │  ├─ open.ts           # PRAGMA, подключение
│  │  ├─ migrate.ts        # runner
│  │  ├─ seed.ts           # workspace/user/pipeline/stages
│  │  └─ migrations/       # 0001_init.sql, ...
│  ├─ http/                # ошибки, пагинация, request context, async-обёртки
│  ├─ audit/               # запись AuditEvent
│  └─ modules/
│     ├─ meta/
│     ├─ companies/
│     ├─ contacts/
│     ├─ leads/
│     ├─ deals/
│     ├─ activities/
│     ├─ tasks/
│     ├─ dashboard/
│     ├─ search/
│     ├─ export/
│     └─ audit/
├─ shared/                 # API-типы, enum-константы, Zod-схемы, форматтеры денег
├─ src/                    # React SPA
│  ├─ app/                 # router, providers, layout
│  ├─ api/                 # fetch-клиент, query keys
│  ├─ features/            # companies, contacts, leads, deals, tasks, dashboard
│  ├─ components/          # переиспользуемые примитивы
│  ├─ i18n/ru.ts           # все пользовательские строки
│  └─ styles/              # tokens.css, base.css
├─ data/                   # runtime-файл БД, в .gitignore
├─ docs/
└─ package.json
```

Каждый модуль сервера имеет `routes.ts`, `service.ts`, `repository.ts`, `schemas.ts`. Роут отвечает за HTTP и валидацию, сервис — за инварианты, транзакции и аудит, repository — только за SQL. Модули не импортируют чужие `repository.ts`; переиспользование идёт через сервисы или общие read-модели.

### Контракты и типы

- REST, JSON, `camelCase` в API; `snake_case` в БД. Преобразование — на границе repository.
- Базовый путь `/api/v1`, кроме `GET /api/health`.
- `shared/` — единственный источник типов запросов/ответов. Backend валидирует вход Zod-схемами из `shared/`, frontend использует выведенные типы. Дублирование DTO в `src/` запрещено.
- Все ID — целые числа (`INTEGER PRIMARY KEY`), в JSON — `number`.
- Деньги — целые минорные единицы и ISO-код валюты; поддерживаются только валюты с экспонентой 2 (список в `domain.md`). `float` для денег запрещён на всех слоях.
- Время в API и БД — UTC ISO 8601; календарные даты — `YYYY-MM-DD`. Отображение — в часовом поясе текущего пользователя из `GET /meta`.
- Ошибки — единый конверт `{ error: { code, message, details?, requestId } }`; коды и статусы зафиксированы в `api.md`.
- Неизвестные поля тела и query-параметры отклоняются с `400 VALIDATION_ERROR`, чтобы контракт не расходился молча.

### Данные

- Один файл SQLite; при открытии: `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`, `synchronous=NORMAL`.
- Все доменные таблицы, кроме `workspace` и `schema_migrations`, содержат `workspace_id`; каждый запрос фильтрует его по контексту запроса, а не по входным данным (см. ADR 0002).
- Миграции — только вперёд. Откат — восстановление из резервной копии, отдельного `down` нет.
- Seed идемпотентен: workspace `1`, пользователь `1`, membership `owner`, pipeline `1`, пять стадий. Seed выполняется после миграций при старте.
- `updated_at` и `created_at` ставит приложение; БД не содержит триггеров аудита. Аудит пишет сервисный слой, потому что ему нужен актор и дифф полей.
- SQL только параметризованный. Динамические сортировки — из белого списка, не из строки запроса.

### Тесты и проверки

- `npm test` — `node --import tsx --test`; каждый тест поднимает приложение на порту `0` и отдельную БД `:memory:` с применёнными миграциями и seed.
- `npm run typecheck`, `npm run lint`, `npm run build` обязательны перед сдачей.
- Тесты проверяют HTTP-контракт, а не внутренние функции: коды, тела, заголовки, отсутствие утечек.
- Frontend: typecheck, lint, production build; критические сценарии проверяются вручную или browser-автоматизацией QA. Отдельный unit-фреймворк для React в MVP не вводится.

### Конфигурация

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `HOST` | `127.0.0.1` | интерфейс прослушивания |
| `PORT` | `3001` | порт Express |
| `DATABASE_PATH` | `./data/flakcrm.db` | файл SQLite; `:memory:` допустим в тестах |
| `WORKSPACE_NAME` | `flakCRM` | имя workspace при первом seed |
| `WORKSPACE_TIMEZONE` | `Europe/Moscow` | IANA-зона для границ отчётов |
| `BASE_CURRENCY` | `RUB` | валюта по умолчанию |
| `LOCAL_USER_NAME` | `Владелец` | имя единственного пользователя |
| `LOCAL_USER_EMAIL` | `local@flakcrm.local` | email единственного пользователя |

Env читается один раз при старте. Значения workspace и пользователя применяются только при первом создании БД; последующие изменения env их не перезаписывают. Секретов в приложении нет.

## Почему этот выбор подходит

1. **Один процесс, один файл БД.** Нет Docker, внешней БД, миграционного сервиса и очередей. Пользователь запускает `npm run dev`, данные лежат рядом с проектом.
2. **Типобезопасность без генераторов.** Zod-схемы в `shared/` дают и runtime-валидацию, и типы. Нет кодогенерации, OpenAPI-пайплайна и рассинхронизации.
3. **SQLite достаточно.** Один пользователь, десятки тысяч записей, редкие конкурентные записи. WAL и `busy_timeout` закрывают сценарий; ограничения по объёму и одному писателю зафиксированы в рисках.
4. **`node:sqlite` убирает нативную зависимость.** Не нужны `better-sqlite3`, node-gyp и пересборка под версию Node. API инкапсулирован в `server/db`, поэтому возможная несовместимость целевой версии Node лечится в одном месте.
5. **SPA без SSR.** CRM — закрытый локальный инструмент; SEO, серверный рендеринг и публичные страницы не нужны. Vite даёт быстрый цикл, Express в production раздаёт статику.
6. **React Router + TanStack Query.** Маршруты и загрузка данных разделены; кеш, инвалидация и состояния списков не пишутся вручную. Собственный CSS удерживает вес и стилистику без UI-кита.

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
| --- | --- |
| Next.js + Prisma + PostgreSQL | SSR и серверные экшены не нужны локальной CRM; PostgreSQL требует отдельного сервиса и администрирования; Prisma добавляет генерацию, бинарники и свой слой миграций. Выше цена запуска и поддержки при том же результате. |
| NestJS + TypeORM/Drizzle + PostgreSQL | DI, декораторы и модульная церемония избыточны для ~10 доменных модулей; TypeORM тянет неявные запросы и N+1; PostgreSQL снова внешний процесс. Drizzle ближе, но всё равно требует отдельного драйвера и gen-шага. |
| Fastify + Drizzle + SQLite | Технически близкий вариант, но Express 5 выбран пользователем; экосистема middleware и примеров для Express шире, а производительность на локальной нагрузке не является ограничением. |
| Django/Laravel + SQLite | Быстрый CRUD «из коробки», но второй язык и другой контракт типов; TypeScript-монорепо и общие DTO дают лучшую типобезопасность на границе SPA↔API. |
| Отдельный frontend-сервер (nginx) | Лишний процесс и конфигурация; Express уже обслуживает API и может раздавать статику. |

## Последствия

**Положительные**

- Минимум инфраструктуры и зависимостей; запуск и бэкап сводятся к файлу БД.
- Единый язык и общие типы на обеих сторонах.
- Быстрый цикл разработки: `tsx watch` + Vite HMR.
- Легко тестировать HTTP-контракт на in-memory БД.

**Отрицательные и принятые**

- Нет ORM: SQL, джойны и маппинг пишутся вручную. Компенсация — repository-слой, единые хелперы пагинации и тесты на каждый запрос.
- SQLite имеет одного писателя. Для одного пользователя это норма; долгие экспорты ограничены 100 000 строк, запись — короткими транзакциями. Переход на PostgreSQL потребует нового ADR.
- `node:sqlite` привязан к версии Node. Целевая версия — Node 26; адаптер в `server/db` изолирует API. Понижение версии Node без проверки не допускается.
- Ручные SQL-миграции требуют дисциплины: каждое изменение схемы — новый файл, проверка на чистой БД, обратная совместимость в пределах инкремента.
- SPA не индексируется поисковиками — для локальной CRM это не требование.
- Нет встроенного планировщика/очередей; фоновые задачи в MVP отсутствуют.

## Правила изменения стека

- Смена runtime, сервера, БД, UI-фреймворка или подхода к контрактам — только новым ADR с анализом миграции и стоимости.
- Добавление зависимости — с обоснованием в задаче: какую проблему решает, чем заменима, цена поддержки. Запрещены UI-киты, ORM, state-менеджеры и библиотеки компонентов без отдельного ADR.
- Версии фиксируются lock-файлом; обновление major-версий — отдельная задача с прогоном тестов и сборки.
- `AGENTS.md` в части «стек не зафиксирован» считается устаревшим после этого ADR; обновление `AGENTS.md` выполняет `crm-lead`.
