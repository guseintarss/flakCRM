# ADR 0002 — Однопользовательский локальный режим без авторизации

- **Статус:** заменён ADR 0003
- **Дата:** 2026-11-10
- **Область:** доступ, модель workspace, API
- **Связанные документы:** `AGENTS.md`, `docs/adr/0001-stack.md`, `docs/adr/0003-multi-tenant-network.md`, `docs/architecture/domain.md`, `docs/architecture/api.md`

> Исторический документ. Описанный режим действовал до появления сети бизнесов.
> Сейчас сервер использует сессии, членство и отдельную базу на бизнес — см.
> ADR 0003 и `docs/architecture/network.md`.

## Контекст

`AGENTS.md` описывает многопользовательскую CRM: workspace, membership, роли `owner/admin/manager/sales_rep/viewer`, авторизацию на каждом эндпоинте и объектную область видимости. Пользователь явно изменил вводные для MVP:

- CRM без авторизации;
- пользователь один;
- локальное использование на своей машине;
- при этом данные хранятся в базе, а не в памяти и не в localStorage.

Игнорировать каноническую модель workspace нельзя: она определяет форму данных и будущую миграцию. Вводить полноценный логин, пароли и матрицу ролей для одного человека — лишняя стоимость и трение, которых пользователь не просил.

## Решение

1. В БД существуют ровно один `workspace` (id `1`), один `user` (id `1`) и одна `membership` с ролью `owner`. Они создаются seed-ом при первом запуске.
2. Аутентификации и сессий нет. Сервер при каждом запросе сам подставляет контекст: `workspaceId = 1`, `currentUserId = 1`. Эти значения никогда не читаются из тела, query, заголовков или cookie.
3. Авторизационных проверок ролей нет: единственный пользователь — `owner`, ему разрешены все действия MVP. Матрица «роль × действие» в MVP не применяется.
4. Все доменные таблицы и запросы сохраняют `workspace_id`. Ни один repository-метод не выполняет запрос без фильтра по workspace. Это делает будущее добавление второго workspace изменением слоя аутентификации, а не переписыванием схемы.
5. Поля владельца (`owner_id`, `author_id`, `assignee_id`) остаются в схеме и заполняются текущим пользователем. API не принимает владельца из входных данных; в ответах он присутствует как справочная информация.
6. Сервер по умолчанию слушает `127.0.0.1`. Публикация в локальную сеть без аутентификации запрещена.
7. API отклоняет `workspaceId`, `workspace_id`, `userId` и `ownerId` в теле как неизвестные поля. Это защита от случайного появления «клиентского» выбора workspace.

## Альтернативы

| Вариант | Почему отклонён |
| --- | --- |
| Полноценная аутентификация с логином, паролем и сессиями | Пользователь один и работает локально; экран входа и управление паролем не создают ценности. Усложняет запуск, тесты и восстановление доступа. |
| «Фейковый» логин с заранее известным пользователем | Даёт иллюзию защиты, но не защищает; добавляет мёртвый код и вводит в заблуждение. |
| Убрать workspace и membership из схемы | Ломает канон `AGENTS.md`, усложняет будущий переход к многопользовательскому режиму и создаёт риск забыть tenant-фильтр позже. |
| Доверять `workspaceId` из запроса | Нарушает инвариант изоляции: клиент смог бы читать чужие данные после появления второй организации. Недопустимо даже в однопользовательском MVP. |

## Последствия

**Положительные**

- Нет экранов входа, паролей, токенов, CSRF и сброса доступа.
- Один пользователь сразу получает полный доступ; запуск сводится к `npm run dev`.
- Схема и запросы уже tenant-safe, что снижает цену будущего многопользовательского ADR.
- Аудит и история стадий сохраняют актора (единственного пользователя), поэтому журнал остаётся осмысленным.

**Отрицательные и принятые**

- Любой процесс/пользователь ОС, имеющий доступ к машине и файлу БД, имеет полный доступ к CRM. Это принятая модель угроз локального инструмента.
- Роли, объектная область `manager`/`sales_rep` и разграничение «свои/командные» записи не реализуются. Соответствующие пункты `AGENTS.md` считаются отложенными до ADR о многопользовательском режиме.
- Сервер нельзя выставлять в LAN/интернет. Если это потребуется, сначала принимается ADR об аутентификации; текущая конфигурация этого не разрешает.
- Смена пользователя/workspace через env после первого запуска не применяется: seed не перезаписывает существующие данные.

## Путь миграции к многопользовательскому режиму

1. Добавить таблицы сессий/токенов и эндпоинты входа.
2. Заменить фиксированный контекст на резолвер сессии; сигнатуры сервисов уже принимают `workspaceId` и `actorId`.
3. Включить матрицу ролей и объектную область на уровне сервисов; DTO и схема БД не меняются.
4. Добавить управление membership и приглашения.
5. Обновить ADR 0002 новым ADR; текущий документ оставить как историю решения.

## Проверки, которые обязательны уже сейчас

- Попытка передать `workspaceId`/`workspace_id`/`ownerId` в теле создания или изменения возвращает `400 VALIDATION_ERROR`.
- Repository-тесты проверяют, что выборки не возвращают строки с другим `workspace_id` (в тесте создаётся вторая строка напрямую в БД).
- Сервер отказывается стартовать, если `HOST` не является loopback-адресом (`127.0.0.1`, `::1`, `localhost`). Публикация в LAN без аутентификации запрещена; отдельного флага обхода в MVP нет.
