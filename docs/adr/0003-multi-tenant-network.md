# ADR 0003 — Мультитенантная сеть бизнесов на отдельных базах

- **Статус:** принято
- **Дата:** 2026-11-16
- **Заменяет:** ADR 0002 (однопользовательский локальный режим)
- **Дополняет:** ADR 0001 (стек; ограничение «публичных страниц нет» снято)

## Контекст

Исходный flakCRM был локальным однопользовательским инструментом: одна база,
один workspace с `id = 1`, без авторизации. Новая задача — превратить его в центр
сети бизнесов и дать одному развёртыванию обслуживать несколько компаний:

- у каждой компании свой вход, свои данные, свой сайт и свои заявки;
- один и тот же код обслуживает рестораны, сервисные компании и туризм;
- владелец настраивает бизнес без программиста и без отдельного деплоя;
- заявки с публичного сайта сразу попадают в CRM этого бизнеса.

Требование «одно приложение — несколько бизнесов одной вертикали, каждый настроен
отдельно» исключает схему «отдельный процесс/деплой на клиента». При этом
существующие сервисы CRM жёстко завязаны на `workspace_id = 1`, а данные
бизнесов должны быть изолированы не только фильтром в запросе.

## Решение

1. **Центральный реестр + отдельная SQLite-база на бизнес.**
   `registry.db` хранит аккаунты, бизнесы, членство и сессии. Каждый бизнес
   получает файл `data/tenants/tenant-<random>.db` с полной схемой CRM и
   таблицами сайта (`site_config`, `site_item`, `site_request`).
2. **Один Node/Express-процесс.** Он обслуживает кабинет, API конструктора,
   публичные сайты и CRM. Публичный сайт и CRM читают одну и ту же базу
   бизнеса.
3. **Контекст бизнеса через `AsyncLocalStorage`.** Существующие роутеры
   `/api/v1` получают прокси-объект `Db`. Внутри авторизованного запроса прокси
   указывает на базу активного бизнеса. Сервисы продолжают использовать
   `workspace_id = 1`, потому что в своей базе бизнес действительно один.
4. **Сессии вместо «локального пользователя».** Пароли — `scrypt` с солью.
   Сессия — случайный opaque-токен в HttpOnly cookie `flakcrm_session`;
   в реестре хранится только SHA-256 токена. Поддерживается `Authorization:
   Bearer` для API-клиентов. Срок — 7 дней.
5. **Членство — единственный источник доступа.** Аккаунт видит только бизнесы,
   где есть запись `membership`. Переключение меняет активный `tenant_id`
   сессии. Чужой `tenantId` отклоняется.
6. **Вертикаль — шаблон, а не отдельный код.** `restaurant`, `service`,
   `tourism` задают подписи, вид каталога и поля формы. Схема данных общая.
7. **Заявка = лид.** Публичная заявка транзакционно создаёт лид и запись
   `site_request` со ссылкой на него. Статус заявки читается из статуса лида,
   поэтому в CRM и конструкторе нет двух расходящихся статусов.
8. **Публикация — явный флаг.** Пока сайт не опубликован, публичный API
   возвращает 404. Черновик не утекает наружу.

## Почему не другие варианты

| Вариант | Почему отклонён |
| --- | --- |
| Общая БД и `tenant_id` во всех таблицах | Требует переписать каждый запрос и каждый индекс, легко получить утечку из-за забытого `WHERE tenant_id = ?`. Существующие сервисы уже используют `workspace_id = 1`; пришлось бы менять доменную модель целиком. |
| Отдельная БД/деплой на каждого клиента | Не выполняет требование «одно приложение обслуживает несколько бизнесов», усложняет обновления и биллинг. |
| PostgreSQL + RLS | Даёт хорошую изоляцию, но добавляет внешний сервис, администрирование, драйвер и миграции. Для текущего объёма и локального стека это лишняя инфраструктура. |
| Отдельный поддомен и сертификат на бизнес | Усложняет запуск и требует DNS/ACME. На MVP публичный путь `/s/<slug>` достаточен. |
| Микросервис реестра | Сетевые вызовы и ещё один процесс без выигрыша для SQLite-нагрузки. |

## Последствия

### Положительные

- Сильная изоляция: запрос физически не может прочитать таблицу другого
  бизнеса, если открыта не та база.
- Существующие CRM-сервисы переиспользуются без переписывания на tenant-aware
  SQL.
- Резервное копирование и удаление бизнеса сводятся к файлу БД + записи
  реестра.
- Один деплой и один набор миграций для всех вертикалей.
- Владелец может вести несколько бизнесов из одного аккаунта.

### Отрицательные и принятые риски

- Реестр — единая точка отказа. Его нужно включать в каждую резервную копию.
- Возможны «осиротевшие» файлы БД, если создание бизнеса упало после создания
  файла: запись реестра удаляется, файл остаётся. Это безопаснее, чем удалить
  данные при неясной ошибке.
- Все открытые базы кешируются в процессе. Для сотен одновременно активных
  бизнесов потребуется LRU-вытеснение и подсчёт ссылок.
- SQLite и WAL рассчитаны на один процесс; горизонтальное масштабирование с
  общей ФС не поддерживается.
- Нет ролей кроме владельца и нет приглашений сотрудников.
- Публичные сайты — SPA без SSR, поэтому SEO ограничено.

## Инварианты

1. `tenant.db_path` в реестре — единственный авторитетный путь к базе бизнеса.
2. Любой `/api/v1/*` и `/api/network/*` требует валидной сессии.
3. `tenant_id` в сессии обязан присутствовать в членстве аккаунта.
4. Публичный сайт доступен только при `site_config.is_published = 1`.
5. `site_request.lead_id` всегда ссылается на лид в той же базе.
6. Публичная заявка и её лид создаются в одной транзакции.
7. Вертикаль бизнеса не меняется после создания.
8. Демо-аккаунт с известным паролем не создаётся в production без явного
   `SEED_DEMO=true`.
9. Старая `data/flakcrm.db` не используется сетевым приложением и не мигрирует
   автоматически.

## Миграция

- Схема базы бизнеса — `user_version 2`: к версии 1 добавлены таблицы сайта.
- Реестр — `user_version 1`.
- Новые базы создаются при провижининге, существующие проходят миграцию при
  открытии.
- Старый `createApp(db)` сохранён для тестов и обратной совместимости, но
  `server/index.ts` запускает только сетевую сборку.
