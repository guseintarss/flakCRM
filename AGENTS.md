# flakCRM — контекст проекта

flakCRM — CRM для управления B2B-продажами. Проект создаётся с нуля командой агентов. Этот файл — общий контекст, границы продукта и контракт качества. Читай его перед любой задачей.

## Продуктовый объём MVP

- Мультитенантная сеть: один деплой обслуживает несколько бизнесов, у каждого своя база.
- Аккаунты, вход, членство и переключение между бизнесами.
- Конструктор сайта и публичный сайт бизнеса: профиль, каталог, публикация.
- Заявки с сайта: бронь столика, вызов мастера, бронирование проживания → лид в CRM.
- Вертикальные шаблоны: ресторан, сервисный бизнес, туризм и размещение.
- Workspace (организация), пользователи и роли.
- Компании и контакты; дедупликация по нормализованному домену и email.
- Лиды и конвертация лида в компанию, контакт и сделку.
- Воронки и стадии; сделки; представления «канбан» и «таблица».
- Активности (звонок, письмо, встреча, заметка), задачи и timeline записи.
- Поиск, фильтры и сохранённые представления.
- Дашборд: пайплайн по стадиям, won/lost, активность за период.
- CSV-импорт и экспорт.
- Аудит изменений.
- Минимальные in-app уведомления.

Вне MVP: биллинг, маркетинговая автоматизация, телефония, мобильные приложения, AI-скоринг, собственные домены, загрузка файлов. Не добавляй это без явного требования пользователя.

Продукт должен оставаться понятным владельцу небольшого бизнеса: настройка сайта без программиста, быстрые списки, минимум кликов до действия, предсказуемые формы.

## Режим работы и доступ

Приложение мультитенантное: один процесс обслуживает несколько бизнесов (ADR 0003). Аккаунт видит только бизнесы, где у него есть членство; данные каждого бизнеса лежат в отдельной SQLite-базе. Активный бизнес хранится в серверной сессии, а не приходит из тела запроса.

- Вход обязателен для `/api/v1` и `/api/network`.
- Публичный API `/api/public` отдаёт только опубликованные сайты и принимает заявки.
- Пароли — `scrypt`, сессии — opaque-токен в HttpOnly cookie; в реестре только SHA-256.
- По умолчанию сервер слушает loopback. Для внешнего доступа обязательны HTTPS и `COOKIE_SECURE=true`.
- Публикация в интернет допустима только с аутентификацией кабинета; публичные сайты — осознанно открытая поверхность.
- Старый однопользовательский `createApp(db)` сохранён для тестов и не используется в `server/index.ts`.

## Доменная модель (канон)

- Реестр сети: `Account` → `Membership` → `Tenant`; `Session` хранит активный бизнес.
- `Tenant` — бизнес с вертикалью `restaurant | service | tourism` и отдельной базой.
- `Workspace` → `Membership` → `User` — локальная модель внутри базы бизнеса.
- `SiteConfig` — профиль и публикация сайта; `SiteItem` — меню/услуги/номера; `SiteRequest` — заявка, связанная с лидом.
- `Company` — организация-клиент: название, домен, отрасль, владелец, теги.
- `Contact` — человек: имя, email, телефон, компания, владелец, теги.
- `Lead` — необработанный контакт/возможность: источник, статус, владелец, ссылки на созданные сущности после конвертации.
- `Pipeline` → `Stage` → `Deal` — воронка, упорядоченные стадии, сделка.
- `Deal` — сумма, валюта, стадия, компания, основной контакт, владелец, статус (`open` / `won` / `lost`), ожидаемая дата закрытия, причина проигрыша, версия.
- `Activity` — звонок, письмо, встреча или заметка; привязка к сущности, время, автор.
- `Task` — задача: срок, статус, исполнитель, приоритет, привязка к сущности.
- `AuditEvent` — кто, что, когда изменил; старые и новые значения для значимых полей.
- `Attachment`, `SavedView`, `Notification`.
- `IntegrationConnection` и `ExternalRef` — подключения и соответствие внешних идентификаторов.

Схему можно расширять, но канонические сущности и их смысл не переименовывай без ADR.

## Инварианты

Нарушение любого пункта — блокер, даже если сценарий «работает».

1. **Изоляция бизнеса.** Данные читаются только из базы активного tenant. Членство проверяется на сервере; `tenantId`, `workspaceId` и `ownerId` не принимаются из тела как основание доступа.
2. **Авторизация на сервере.** Проверка права и объектной области — на каждом эндпоинте. Скрытая кнопка не считается защитой.
3. **Деньги.** Суммы хранятся целыми числами в минорных единицах вместе с ISO-кодом валюты. Никаких float для денег.
4. **Время.** В хранилище и API — UTC; часовой пояс пользователя применяется только при отображении и в отчётах.
5. **Мягкое удаление.** CRM-записи удаляются мягко; жёсткое удаление — только явная административная операция с аудитом.
6. **Стабильные списки.** Любой список пагинирован, имеет детерминированную сортировку и ограничение размера страницы.
7. **Аудит.** Создание, изменение и удаление значимых сущностей пишут `AuditEvent`; секреты и лишние PII в аудит не попадают.
8. **Конвертация лида.** Атомарна и идемпотентна: повторный вызов не создаёт дублей.
9. **Сделка.** Смена стадии создаёт запись истории; переход в `won`/`lost` требует причины для `lost` и фиксирует дату закрытия.
10. **Конкурентные изменения.** Редактирование сделки защищено версией/`updated_at`; конфликт возвращает понятную ошибку, а не перезаписывает чужие данные.
11. **Дедупликация.** Email и домены нормализуются перед сравнением; правила поиска дублей едины для импорта и ручного создания.
12. **Валидация.** Все входные данные проверяются схемой на сервере. Клиентская валидация — только удобство.
13. **Секреты и PII.** Секреты — только через env/секрет-хранилище. В логах, ошибках и аудите нет токенов и лишних персональных данных.
14. **Импорт.** Импорт идемпотентен, поддерживает dry-run, отчёт по строкам и не оставляет частично записанных батчей без объяснения.

## Стек

Стек зафиксирован ADR 0001:

- TypeScript, Node.js 22.13+ (проверено на Node 26), Express 5, SQLite через встроенный `node:sqlite`.
- React 19 + Vite + React Router + TanStack Query, собственный CSS.
- Один репозиторий: `server/` + `src/` + `shared/`; Vite proxy на `/api`, в production Express раздаёт собранный клиент.
- Тесты сервера: `node:test` + `tsx`, in-memory SQLite для CRM и временный каталог для сети.

Смена стека — только новым ADR с обоснованием.

## Команда агентов

| Агент | Зона ответственности |
| --- | --- |
| `crm-lead` | Планирует инкременты, делегирует, интегрирует, проверяет результат. Главный агент проекта. |
| `crm-architect` | Продуктовый срез, доменная модель, API-контракты, ADR и план работ. Код не пишет. |
| `crm-backend` | Схема БД, миграции, доменные сервисы, API, авторизация, аудит, фоновые задачи и тесты. |
| `crm-frontend` | Экраны CRM, таблицы, канбан, формы, состояния, доступность и клиентские тесты. |
| `crm-integrator` | CSV-импорт/экспорт, webhooks, email/calendar sync и другие внешние адаптеры. |
| `crm-qa` | Независимое ревью: изоляция, права, инварианты, регрессии, доступность, безопасность. Код не меняет. |

## Рабочий цикл

1. **Срез.** `crm-lead` выбирает один вертикальный срез, который можно довести до проверяемого результата за инкремент.
2. **Контракт.** `crm-architect` уточняет модель, API, права, миграции и критерии приёмки; обновляет план и ADR.
3. **Реализация.** `crm-backend` и `crm-frontend` работают параллельно только на зафиксированном контракте и непересекающихся файлах. `crm-integrator` подключается, когда срез затрагивает внешние данные.
4. **Проверка.** `crm-qa` проверяет срез по матрице рисков и запускает тесты. Найденные блокеры возвращаются владельцу зоны.
5. **Приёмка.** `crm-lead` сам запускает проверки, читает diff и проходит критический сценарий. Без доказательств инкремент не принят.

Правила работы:

- Сначала контракт, потом код. Несовпадение с контрактом — не «мелкая деталь», а дефект.
- У каждого файла и модуля один владелец в рамках задачи; параллельные правки одной зоны запрещены.
- Изменение публичного API, схемы или стека — только через архитектора и ADR.
- Репозиторий после каждого инкремента собирается, тесты проходят, миграции применяются на чистой базе.
- Не оставляй заглушки, «временные» обходы прав и закомментированный код без явной задачи и пометки.

## Definition of Done

- Критерии приёмки среза выполнены, поведение проверено вручную или e2e-тестом.
- Есть тесты на новые инварианты, включая негативные сценарии: чужая организация, недостаточная роль, невалидные данные, повторный вызов.
- Проходят typecheck, lint, тесты и сборка проекта.
- Миграции безопасны и проверены на чистой базе; данные не теряются.
- UI: состояния загрузки, пустоты и ошибки; клавиатура и фокус; адаптивность от 320 px; понятные тексты ошибок.
- Нет секретов в коде, N+1 на горячих списках и неограниченных выборок.
- План/ADR/документация обновлены, если решение изменилось.
- В отчёте есть команды проверок и их результат.

## Конвенции

- Идентификаторы, типы и имена файлов — на английском; пользовательские тексты — на языке продукта, через слой локализации, без хардкода в компонентах.
- Ошибки API — единый формат, зафиксированный архитектором; коды машинно-читаемые, сообщения понятны пользователю.
- Даты, деньги и телефонные номера форматируются централизованно, а не в каждом компоненте.
- Новые зависимости — только с обоснованием: что решает, чем заменима, цена поддержки.
